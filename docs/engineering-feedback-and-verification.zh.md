# Eve 深度工程化反馈与可验证性方案

## 目标

这份方案解决一个根本问题：

- 没有结构化反馈，优化只能靠体感和零散日志
- 没有可验证性，任何“变快了 / 变好了 / 更稳定了”都无法被证明
- 没有统一 UX 确认方法，产品体验只能依赖主观印象

对于 `Eve` 这样的实时录音、ASR、说话人识别、实时翻译、录后复核一体化项目，必须把“反馈”和“验证”做成一等公民。

## 结论先行

仅靠日志不够。

一个深度工程化项目至少要同时具备 6 类反馈能力：

1. 结构化日志
2. 时延与质量指标
3. 可复现样本与回放能力
4. UX / UI 确认标准
5. 分层测试体系
6. 发布门禁与回归对比

如果没有这些：

- 无法定位问题到底出在 VAD、ASR、翻译队列、网络还是 UI
- 无法证明优化是否真的改善了体验
- 无法把一次用户反馈沉淀成长期质量提升资产

## 当前项目已具备的基础

当前分支已经具备一部分基础能力：

- `Live Stage` 诊断区
- 结构化 `SegmentRecord`
- `translationError`
- `Review & Learn`
- 句级修正与候选规则
- 主进程日志

这些能力说明项目已经不再是“只有界面和功能”，但还没有到“强可观测、强可验证”的工程状态。

## 当前缺口

目前最关键的缺口是：

1. 没有记录每段 raw 首发时间
2. 没有记录每段翻译排队、开始、首块返回、整段完成的时间
3. 没有把网络失败、401、模型回显中文等情况统一成可统计错误码
4. 没有“黄金样本集”来比较不同版本的翻译质量和时延
5. 没有会场级 UX 确认清单
6. 没有发布前门禁来证明新版本比旧版本更好

## 方案总览

### 一、结构化反馈面

项目反馈不应只包含 `console`/文件日志，还应包括：

- 结构化事件
- 结构化时延
- 结构化错误
- 结构化用户修正
- 结构化体验评价

建议把反馈面分成以下层级：

1. `Operational`
运行是否正常：
- 录音是否开始
- 设备是否切换
- 权限是否正常
- OpenAI 请求是否成功

2. `Latency`
速度是否正常：
- raw 首发耗时
- 首块日文耗时
- 整段翻译完成耗时
- 队列等待耗时

3. `Quality`
结果是否正常：
- 语言识别是否正确
- 翻译是否回显中文
- 说话人是否命中
- 是否需要人工修正

4. `UX`
用户是否真的能用：
- 会场读得清吗
- 当前段优先是否成立
- 右栏空白时间是否可接受
- recent 是否过度干扰主视线

### 二、最小可用时延埋点

每个 `SegmentRecord` 建议新增以下字段：

- `segmentDetectedAt`
- `liveStagePublishedAt`
- `translationQueuedAt`
- `translationStartedAt`
- `translationFirstChunkAt`
- `translationCompletedAt`
- `translationErrorCode`

有了这些字段后，就能直接算：

- `raw 首发延迟 = liveStagePublishedAt - segmentDetectedAt`
- `首块日文延迟 = translationFirstChunkAt - segmentDetectedAt`
- `整段日文延迟 = translationCompletedAt - segmentDetectedAt`
- `翻译排队延迟 = translationStartedAt - translationQueuedAt`
- `OpenAI 首块耗时 = translationFirstChunkAt - translationStartedAt`

这组数据是后续所有性能优化的根基。

### 三、日志应该输出什么

日志要保留，但要明确分层：

1. `session` 级日志
- 启动时间
- 环境变量生效情况
- 模型与运行模式
- 权限与设备

2. `segment` 级日志
- `segmentId`
- 语言路由
- 文本长度
- 说话人命中情况
- 各阶段时间点
- 翻译错误码

3. `queue` 级日志
- 当前 ASR 队列长度
- 当前翻译队列长度
- 是否发生 backpressure
- 是否丢弃旧任务

4. `failure` 级日志
- 网络失败
- 401 / key 错误
- 空翻译
- 原样中文回显
- 说话人样本加载失败

日志建议统一成“人读得懂 + 机器可搜”的格式：

- 保留现有 `electron-log`
- 同时增加关键字段的结构化对象输出

### 四、除了日志，还应该纳入项目反馈范围的内容

日志只回答“系统发生了什么”，但工程质量还需要下面这些反馈资产：

#### 1. 黄金样本集

建立一组固定测试素材：

- 短中文句
- 长中文段
- 日文直出
- 中日混说
- 口语、引号、方言、数字、专有名词

每次版本更新都跑同一批样本，比较：

- 首块日文耗时
- 完成耗时
- 翻译完整率
- 中文回显率
- 说话人命中率

#### 2. 录后复核数据

`Review & Learn` 已经存在，应继续把它作为质量反馈主来源：

- 哪些句子被人工改过
- 改动前后差异
- 哪些说话人更容易误识别
- 哪些类型的句子更容易误译

#### 3. UX 确认记录

每次会场测试都不应该只说“感觉慢”。应形成结构化检查项：

- 当前段是否先于 recent 被关注到
- 右栏是否在 1~2 秒内出现第一块信息
- 大窗口下每行是否足够长
- 观众是否会因跳动而失去阅读节奏

#### 4. 失败样本档案

把失败案例沉淀成真实资产：

- `network_error`
- `invalid_api_key`
- 中文整段回显
- recent 永远不补完
- 说话人误判

每个失败样本都应能回放、复现、比较新旧版本结果。

### 五、UX / UI 的确认方法

UX 不能只靠“看起来差不多”。建议建立固定确认方法：

#### 会场模式检查表

1. 当前段是否占主视觉
2. 左右双语是否能同时读
3. 右栏空白是否超过可接受阈值
4. recent 是否喧宾夺主
5. diagnostics 是否只在排障时可见
6. 窗口大小、字号、行长是否平衡

#### 三档时延体验定义

建议固定三档体验标准：

- `Excellent`
  - 首块日文在短暂停顿后快速出现
  - 几乎不影响观众理解节奏

- `Acceptable`
  - 有明显等待，但观众仍能跟上

- `Poor`
  - 右栏大量空白
  - 当前段结束后仍长时间无日文

每次测试都应该给出这三个等级之一，而不是只给口头印象。

### 六、高级测试方法

建议把测试体系拆成 5 层：

#### 1. Pure unit tests

已经有基础：

- 文本切块
- 队列优先级
- Progressive 替换

继续补：

- 错误码映射
- unchanged echo 判定
- 语言路由判定

#### 2. Engine integration tests

以 `DesktopEngine` 为中心验证：

- segment 产出
- status 变化
- translation 触发与完成
- 失败时的状态与错误码

#### 3. Replay tests

把真实录音或缓存样本喂给 engine：

- 比较不同参数下的 segment 粒度
- 比较不同翻译调度策略的首块日文延迟

#### 4. UX snapshot tests

渲染层验证：

- pending
- streaming
- ready
- failed
- 双语主卡片
- recent 双语卡片

#### 5. Release benchmark tests

每次发布前至少跑：

- 黄金样本集
- 首块日文 P50 / P95
- 错误率
- 中文回显率

### 七、没有反馈和可验证，我们如何改善

答案很直接：

- 不能系统性改善
- 只能靠感觉试错
- 很难知道某次优化到底是在“变快”还是“引入新问题”

没有反馈体系时，所有改动都会退化成：

- 用户说慢
- 工程师猜哪里慢
- 调一个参数
- 再看用户感觉

这不是深度工程化，而是经验式调参。

### 八、除了反馈和可验证，还应该提供什么

除了 `feedback + verification`，还必须提供下面三类能力：

#### 1. Reproducibility

可复现性：

- 同一段输入能重复测试
- 同一版本结果可回放
- 不同版本结果可对比

#### 2. Operability

可操作性：

- diagnostics 可见
- 错误码可见
- 队列状态可见
- 能快速知道现在是 `pending / streaming / failed / ready`

#### 3. Decision support

可决策性：

- 是否值得切换模型
- 是否该优先压 VAD
- 是否该优先压网络 RTT
- 是否该优先牺牲 recent 完整度来保当前段

没有这三类能力，反馈数据再多也难以转化成正确决策。

## 建议分阶段落地

### Phase 1：最小可用埋点

- 为 `SegmentRecord` 增加时延字段
- diagnostics 显示 raw / first ja / complete 耗时
- 统一 `translationErrorCode`

### Phase 2：黄金样本与基准

- 建样本目录
- 固定跑法
- 输出 P50 / P95 / 错误率

### Phase 3：回放与回归平台

- 用真实录音做 engine replay
- 自动对比不同策略结果

### Phase 4：发布门禁

- 新版本若首块日文 P95 变差或错误率上升，则阻止合并 / 发布

## 对当前项目的直接建议

按优先级：

1. 先补结构化时延埋点
2. 再补 diagnostics 的耗时显示
3. 建一套中日会议黄金样本集
4. 建 release benchmark
5. 最后再继续调模型、队列和界面

原因很简单：

- 现在继续只靠体感优化，收益越来越低
- 先把“怎么量化质量”做出来，后面的每一次优化才会更快、更稳

## 产出物建议

建议把这套能力作为项目正式交付的一部分，而不是临时排障能力：

- 项目文档
- 结构化 segment 埋点
- diagnostics 面板
- 黄金样本集
- 基准脚本
- 发布门禁检查

这才是一个实时语音/翻译项目进入深度工程化状态的标志。
